# Nexus relationships: raw file requirements, candidate evidence, and manual review

**Offline research example only**, reviewed 2026-11-22, for [Modding-Knowledge #16](https://github.com/Herbertofury/Modding-Knowledge/issues/16). No live API requests, login, download, cache, native game behavior, service changes, or permission expansion. All JSON response examples are invented. Do not import them.

## What Nexus actually documents

| Surface | Scope and safe interpretation |
|---|---|
| [GraphQL v2](https://graphql.nexusmods.com/#definition-ModRequirements) | Legacy project-level outgoing `nexusRequirements` (including external-link flag, provider-reported game/mod IDs, notes and URL), legacy `dlcRequirements`, and **reverse** `modsRequiringThisMod`. Outgoing and reverse paginated independently by offset/count; never flip a reverse row into an outgoing edge. `legacyModRequirementsEnabled` and `skipDisabledRequirements` distinguish migrated content: skipping can deliberately omit old Nexus and DLC rows. Legacy data does not establish an exact file, range, conflict, or recommendation; text notes can qualify scope and need review. Nexus calls v2 work-in-progress and says much is accessible without credentials, but authorization for this specific selection and live response behavior were not tested. |
| [OpenAPI v3 raw exact file-version requirements](https://api-docs.nexusmods.com/#tag/mods/operation/getModFileVersionDependencies) | `GET /mod-file-versions/{id}/dependencies` uses the **unique v3 file-version ID**. The documented HTTP 200 payload directly exposes `dependency_definitions` and `dlc_dependency_definitions`. Mod-file range groups contain alternatives (OR); separate definitions are independent requirements (AND). Preserve range IDs, target mod/game/update-group identities and exact min/max IDs; the nullable upper bound means open-ended. DLC groups have distinct target IDs and the same OR/AND grouping, not mod files. |
| [OpenAPI v3 candidate batch](https://api-docs.nexusmods.com/#tag/mods/operation/getModFileVersionDependencyRangesMaterializedBatch) | The current read-shaped `POST /mod-file-versions/dependencies/ranges/materialized/batch` is documented; the older path without `ranges` is deprecated. Candidate rows are grouped by exact `(source_version_id, definition_id)`; each group is alternatives, not multiple new requirements. `mod_file_id` identifies an update chain and `version_id` the candidate. Candidate position is documented as higher=newer **within one chain**, not an ordering rule for IDs, across groups, or a decoder-side range evaluator. The schema labels position as a decimal string but specifies no lexical pattern, scale or precision. Preserve it verbatim, without parsing or sorting it in this fixture; do not conflate an optional **file category** with an authored optional **relationship**. Page numbering starts at 1. Nonempty pages alone have useful `meta.total_count`; a requested source with no resolvable candidates may contribute no rows. An empty candidate page does not imply no raw requirement. |
| [OpenAPI v3 version identity](https://api-docs.nexusmods.com/#tag/mods/operation/getModFileVersionByGameScopedId) | Documented `GET /games/{game_domain}/mod-file-versions/{game_scoped_id}` has HTTP 200 `data` containing both `id` and `game_scoped_id`, plus the persistent `file.id`, human display version and exact position. Verify the known game and URL-scoped ID before associating that global/unique response ID with a status or dependency result. The public mod-page number, game-scoped file number, exact global file-version identifier, update-group identifier, composite mod UID and display version are not interchangeable. Candidate `mod_id` is the composite mod UID according to `ModsBatchRequest`, not a mod page number. |
| Conflicts, recommendations, external resources, availability | Neither requirements shape supplies a generic authored conflicts/recommendations/works-with edge. V2 can expose external links in legacy **requirements**, but the checked v3 raw shape has only mod-file ranges and DLC. An explicitly permitted first-party description or changelog can be reviewed manually and attributed at its exact scope. Unknown remains unknown; never subtract requirements, recommend a binary, assert installability, or treat a published candidate/status, removed/hidden/forbidden response or author note alone as eligibility, safety, compatibility, ban or relocation. |

V3 dependency/identity endpoints here are **experimental**, not production guarantees. The published OpenAPI declares API-key or bearer auth for these operations, without an unauthenticated override; check actual capability and permitted application scope separately. Official source audited: [Nexus Vortex OpenAPI, pinned](https://github.com/Nexus-Mods/Vortex/blob/116c8aba95ae2ef31dfdc7083eb909d611d3712a/packages/nexus-api-v3/schema/openapi.yaml), commit `116c8aba95ae2ef31dfdc7083eb909d611d3712a`, blob `6473c6d26b14fe3c75b6d42871ac74ad4d36e171`, SHA256 `c145fbcec8533cae6abe0b352f2acb0ce4b954669c96eb4ab15d0787e046f680`. [Official package README](https://github.com/Nexus-Mods/Vortex/blob/116c8aba95ae2ef31dfdc7083eb909d611d3712a/packages/nexus-api-v3/README.md) identifies the provider-hosted [OpenAPI spec](https://api.nexusmods.com/openapi.yaml) as codegen source; this pass pinned the committed copy instead. [Official Vortex client](https://github.com/Nexus-Mods/Vortex/blob/116c8aba95ae2ef31dfdc7083eb909d611d3712a/packages/nexus-api-v3/src/client.ts) corroborates the current batch route and envelope. No credentials or authenticated endpoint calls made.

## Policy and replay

The [Nexus AUP](https://help.nexusmods.com/article/114-api-acceptable-use-policy) prohibits bulk fetching for rehosting, server-side user-key storage or non-user-initiated key use, personal keys in a public-facing app, and misidentifying clients. It describes registered apps and their true Application-Name and Application-Version. See [Nexus terms](https://help.nexusmods.com/article/18-terms-of-service) for provider limits. A documented route, available page, or authorized keyed client is **not** permission to retain or publish a centralized copy, use third-party assets, or run collection. The [source inventory](../../../SOURCES.md) and [storage contract](../../../docs/storage-api.md) require reviewed fields/retention/publication and separate collection permission. The reviewed snapshot at `d9bf11a2ef472ed0140886a2360c7baf7f080db4` contains no admitted Nexus source; keep this work outside production. Any later authorized source test should preserve last-good evidence on blocked/malformed responses, avoid gated pages, and confirm relevance with the exact installed file only under user control.
